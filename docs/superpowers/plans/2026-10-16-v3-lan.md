# Segurança Integral v3 Implementation Plan

**Status:** concluído em 16/10/2026. [Evidências e limites](../../verificacao-v3.md). Alterações revisáveis em `feature/v1`, instalador LAN 3.0.0 gerado. Percursos de navegador em `frontend/verificacao/v3-lan.mjs` e harnesses locais documentados no relatório de verificação.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Entregar os dois portais redesenhados, questionário com pesos, colaboração em tempo real e operação exclusivamente LAN com CLI.

**Architecture:** Preservar APIs v2 e dados antigos. Acrescentar questionário e envio v3 em rotas distintas, uma definição canônica, retrato histórico de triagem, SSE com invalidações e presença efêmera. Manter um processo gevent e SQLite; monitor CLI somente leitura.

**Tech Stack:** Python/Flask/gevent/SQLite; React/TypeScript/Vite/Vitest; PyInstaller/Inno Setup/PowerShell.

**Spec:** `docs/superpowers/specs/2026-10-16-v3-lan-colaboracao-design.md` (aprovada em 16/10/2026).

## Global Constraints

- Sem serviços externos, outro banco, mudança de firewall local, instalação ou deploy na máquina escolar.
- Anônimo por padrão; código somente em POST, nunca URL/storage/log. Pesos, autoria da equipe e notas não chegam ao aluno.
- Perguntas únicas por ID; seleção múltipla entre oito grupos; validação de alcance no servidor; alternativas neutras peso zero.
- Peso-base máximo das opções + máximo por dimensão; média 5, alta 9, crítica por alertas. Legado preservado.
- Migração idempotente com backup; snapshot histórico; nenhuma alteração retroativa de casos.
- Presença: pulso 10 s, TTL 45 s; SSE heartbeat 15 s; fallback 8 s; watch CLI 2 s.
- Não criar commits automaticamente nesta execução: entregar alterações revisáveis no checkout feature/v1 existente. Usar ledger e diff como evidência.
- Testes antes do código; validação focada por alteração, suítes completas no fechamento de cada fase.

## Review Focus

- Uma definição alterada durante o envio não pode validar com uma versão e pontuar com outra: teste na Task 1.
- Resposta cujo gatilho foi removido em cadeia não pode persistir ou pontuar: Tasks 1 e 2.
- Confirmação perdida após commit não pode duplicar caso/anexos ou expor código em claro: Task 1.
- Logout/desativação durante SSE deve encerrar acesso, sem conexão SQLite retida: Task 3.
- Monitor iniciado em pasta inexistente não deve criar dados, chaves ou servidor: Task 4.

## Estrutura e contratos entre fases

Novos arquivos de backend: `app/questionario_v3.py`, `app/questionario_v3.json`, `app/routes_v3.py`, `app/envios.py`, `app/realtime.py`, `app/routes_realtime.py`, `app/diagnostico.py`, `app/status_cli.py`.
Frontend: `src/shared/v3.ts`, `src/aluno/Pedido.tsx`, `src/aluno/fluxoV3.ts`, `src/aluno/rascunhoV3.ts`, `src/shared/tempoReal.ts`, `src/coord/Presenca.tsx`. Reutilizar anexos, confirmação, conversa e tokens existentes quando útil.

Definição pública v3: `{versao:3, grupos:[{id,nome,opcoes:[{id,texto,perguntas:string[]}]}], comuns:string[], perguntas:[{id,dimensao,texto,tipo:'unica'|'multipla',respostas:[{id,texto}],mostrar_se?:string[]}], dimensoes:Record<string,string>}`. Pesos/alertas/faixas e `tipo_legado` ficam apenas no arquivo privado.

`GET /api/v3/questionario` entrega definição pública. `POST /api/v3/denuncias` multipart mantém campos de relato/anexos existentes e acrescenta `envio_id` (32 hex) e `respostas` JSON `{versao:3,marcadas:string[],respostas:Record<string,string[]>}`. Sem respostas permite relato livre com tipo legado `outro`. Sucesso 201 `{codigo,anexos_recusados?}`; repetição idêntica devolve a mesma confirmação; conteúdo diferente com mesmo recibo dá 409. O endpoint v2 permanece.

`GET /api/casos/<id>` acrescenta `revisao_estado:number`, `categorias:string[]`, `opcoes:string[]`; `questionario` mantém o formato legível atual para reutilizar RespostasAluno, mas vem do snapshot v3. `GET /api/casos` acrescenta categorias/opções para filtro. Filtros v3 `grupo`/`opcao` validam IDs canônicos; o filtro legado `tipo` continua.

SSE coord `GET /api/eventos`; aluno `POST /api/acompanhar/eventos` corpo `{codigo}`. Eventos `event: atualizar` com `data: {}` (todos os dados vêm das leituras autenticadas existentes); primeiro evento sempre invalida. Presença `GET /api/casos/<id>/presenca`, `POST .../presenca` `{aba,atividade:'vendo'|'mensagem'|'nota'}`, `DELETE .../presenca` `{aba}`. Resposta `{pessoas:[{id,nome,atividade}]}`.

Endpoints v3 para ações: `POST /api/v3/casos/<id>/status|prioridade|resolucao|revisao-recorrencia` mesmos campos v2 mais `revisao_estado`. Rotas v2 mantidas. Revisão somente muda com estado, prioridade, resolução ou recorrência; append de mensagem/nota não exige revisão.

CLI usa `GET /api/servidor` em ambas as portas, somente loopback direto. `{produto:'seguranca-integral',versao:'3.0.0',portal:'aluno'|'coordenacao',uptime_s,banco:{ok},backup:{estado:'pendente'|'ok'|'erro',em:string|null},eventos:{assinantes:number}}`. Um estado de runtime compartilhado pelos portais é injetado pelo servidor; factories em testes podem usar estado inicial pendente.
